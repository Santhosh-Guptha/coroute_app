04 · Roles

HOW A REQUEST MOVES

Four rules keep rides safe while servers change

1 · LOAD BALANCER

vm1 first, vm2 as backup

It checks vm1’s health every 5 seconds. If vm1 stops answering, all traffic goes to vm2.

2 · ROUTE SPLIT

Live on vm1, web on vm2

Caddy on vm1 keeps rides and SOS (96 routes) and sends the other 475 routes to vm2.

3 · MIRROR

Every ride exists twice

SOS and alerts are saved to the database first, then copied, then confirmed to the phone.

4 · JOB LEASE

Each background job runs once

Ride jobs prefer vm1, the rest prefer vm2. If one dies, the other takes over after 2 minutes.

STEPS 1–2 · PREPARE AND BACK UP

Nothing changes before a tested backup exists

Prepare

  • Lock or rotate the two admin accounts whose passwords leaked into git history
  • Copy inventory.example.env to inventory.local.env and fill in real values (never committed)
  • Create DATA_ENC_KEY and BLIND_INDEX_KEY in the Vault; same on both servers; keep an offline copy

Back up

ssh vm2 && cd /opt/coroute/gateway
node scripts/backup_export.js --set full
node scripts/backup_restore.js \
  --latest full --dry-run

Without the backup key no backup can be read. Store it in your password manager too.

STEP 3 · SERVER TUNING

One script per role, read the dry run first

sudo ./deploy/host/apply.sh \
  --role realtime --peer-ip <vm2-private> \
  --dry-run

# then without --dry-run
# roles: realtime · web · dr · staging · worker

Safe to run again. It never restarts the gateway or deletes firewall rules.

  • Network and file limits sized for many open connections
  • Swap used only when needed; logs capped at 200 MB
  • Security updates automatic, never reboots
  • SSH keys only, no root, no passwords; fail2ban
  • Firewall: 80/443 public, internal ports only from the peer
  • Gateway restarts itself, with a memory limit

STEPS 4–5 · RELEASES

Staging first, live server last, rollback on its own

BUILD

Bundle with pre-compressed website files

vm4 STAGING

Smoke test + quick load test

vm2 WEB

Health check must pass

vm1 LIVE

Riders drain to vm2, then restart

gateway/deploy/release.sh
gateway/deploy/release.sh --only vm4
gateway/deploy/release.sh --rollback vm1

Each server keeps its previous release. A failed health check switches that server back by itself and stops the release, so vm1 is never touched after a failure on vm4 or vm2.

STEP 6 · DISASTER RECOVERY

vm3 watches, backs up and stands ready

WATCHDOG

Checks every 30 s

Alert email after 3 failures, recovery email, daily summary. vm4 watches vm3.

BACKUPS

Three layers, encrypted

Hourly and nightly in account 1, nightly copy on vm3 (7 daily, 4 weekly, 3 monthly), copy in account 2.

RESTORE TEST

Every Sunday

Decrypts the newest backup, restores it in memory, compares counts, emails the result.

PROMOTE

Manual by default

Only when vm1 and vm2 are both down: one script switches DNS to vm3.

sudo bash deploy/dr/promote_vm3.sh   # refuses while the site is up · demote_vm3.sh to go back

GROWTH PATH

What to do as riders grow

NOW → 1,000 RIDERS

Today’s setup

This release, plus a 2,500-rider cap per micro. Watch vm1’s metrics.

Move on when: over 500 riders for long, or lag over 100 ms for 10 minutes.

1,000 → 5,000

Live rides on Ampere

A free Ampere server in account 1 becomes the live node; vm2 stays the mirror.

Move on when: database over 300 calls/s or Ampere CPU over 60 %.

5,000 → 20,000

Full Ampere pair

4 cores / 24 GB as live node, a second Ampere as its mirror, longer caches.

Beyond 20,000: split groups across two pairs, or a paid database tier.
