How a request moves

Four rules keep rides safe while servers change

1 · LOAD BALANCER

vm1 first, vm2 as backup

The free network load balancer checks /api/health/live on vm1 every 5 s. If vm1 fails, everything goes to vm2. Keep it on the network LB: the 10 Mbps flexible LB would cap traffic at about 1,000 riders.

2 · ROUTE SPLIT

Live on vm1, web on vm2

Caddy on vm1 keeps the 96 live routes (rides, SOS, live links) and sends the other 475 to vm2 over the private network. release.sh stops on an unclassified route.

3 · MIRROR

Every ride exists twice

vm1 and vm2 keep identical rides over an encrypted link. SOS, alerts and chat are saved to the database first, copied, then confirmed to the phone.

4 · JOB LEASE

Each job runs once

Background jobs run on exactly one server. Ride jobs prefer vm1, the rest vm2; the other takes over after a 120 s grace.

Setup flow

Seven steps, in this order

Run from your machine with SSH aliases vm1…vm5. After every step, check health. If a check fails, undo the last step and stop. Never restart vm1 and vm2 together; vm2 always goes first.

  1. Prepare

    • Lock or rotate the two admin accounts whose passwords leaked into git history.
    • Fill the private inventory file (never committed):
    cp gateway/deploy/inventory.example.env gateway/deploy/inventory.local.env
# edit: VM1_PRIVATE_IP, VM2_PRIVATE_IP, public IPs, NLB IP, OCI IDs, hosts
    • Create DATA_ENC_KEY and BLIND_INDEX_KEY in the Oracle Vault (openssl rand -base64 32 each), identical on vm1 and vm2, with an offline copy.

    Check: scripts that read the inventory stop with a clear message if a value is missing.

  2. Back up first

    ssh vm2
cd /opt/coroute/gateway
node scripts/backup_export.js --set full
node scripts/backup_restore.js --latest full --dry-run

    Check: the dry run decrypts the backup and matches its manifest. Keep BACKUP_ENCRYPTION_KEY in your password manager too: without it no backup can be read.

  3. Tune each server

    sudo ./deploy/host/apply.sh --role web --dry-run          # vm2: read the diff
sudo ./deploy/host/apply.sh --role web
sudo ./deploy/host/apply.sh --role realtime --peer-ip <vm2-private>   # vm1
# other roles: dr (vm3), staging (vm4), worker (vm5)

    Network and file limits, swap only when needed, capped logs, automatic security updates (never reboots), SSH keys only with fail2ban, firewall per role, gateway restart policy with a memory limit. It never restarts the gateway itself. Set the load balancer health check to HTTPS /api/health/live, every 5 s, timeout 3 s, 2 retries.

    It refuses to disable SSH passwords if your user has no SSH key: add your key first.

  4. Staging on vm4

    gateway/deploy/release.sh --only vm4
gateway/deploy/staging/smoke.sh https://staging.coroute.devmonks.space
gateway/deploy/staging/quick_load.sh

    Check: smoke prints OK; the quick load test passes. Staging uses its own database (the seeding tool refuses production).

  5. Release to production

    gateway/deploy/release.sh            # vm4 → (confirm) vm2 → (confirm) vm1
gateway/deploy/release.sh --rollback vm1

    Each server unpacks into its own release folder, switches a symlink, restarts and must pass its health check, or switches back on its own and stops the release. Then install the matching Caddyfile, vm2 first:

    sudo cp /opt/coroute/gateway/deploy/caddy/Caddyfile.vm2 /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy

    Check: curl -s http://127.0.0.1:3000/api/health says HEALTHY on each server; the public smoke test passes.

  6. Disaster recovery on vm3

    sudo SECRETS_MODE=vault DR_TLS=dns bash deploy/dr/install_standby.sh
gateway/deploy/release.sh --only vm3
sudo systemctl enable --now coroute-watchdog
sudo systemctl enable --now coroute-backup.timer coroute-restore-drill.timer

    Check: /api/health/live on vm3 answers 503 “standby” (correct); the first watchdog summary email arrives; the restore test email says counts match.

  7. vm5 when it arrives

    Apply the worker role, then each job only after the owner says yes: Valhalla routing (switch with ROUTER_KIND=valhalla after a week of side-by-side checks), map tiles, a private road-data server, Umami analytics, batch jobs.

Release rules

Every release, every time

  • Order: build → vm4 staging → vm2 → vm1. vm1 is never touched after a failure earlier in the chain.
  • Gateway before app: deploy the gateway first, then publish the APK. One gateway serves every app version; each new feature checks the app version.
  • Version settings: set LATEST_APP_BUILD to the newest build so older apps are offered the update. Raise MIN_APP_BUILD only when an old build must stop working.
  • Drain: with SHUTDOWN_DRAIN_MS=15000 the load balancer moves riders to vm2 before vm1 restarts.

Watchdog: checks the site, vm1 and vm2 every 30 s; one alert email after 3 failures, one recovery email, a daily summary. vm4 watches vm3.

Promote vm3 (manual by default), only when vm1 and vm2 are both down:

sudo bash deploy/dr/promote_vm3.sh   # refuses while the site answers; asks before each step
sudo bash deploy/dr/demote_vm3.sh    # after vm1/vm2 are healthy again

Certificates are obtained on vm3 in advance, so promotion only switches DNS. Never run vm1 and a promoted vm3 together longer than the switch: they don’t mirror each other.

Security

Locked down by default

  • SSH: keys only, no root, no passwords, fail2ban.
  • Firewall: 80/443 public; internal ports (3000, 3101) only from the peer’s private address; Oracle security lists as the outer layer.
  • Secrets: Oracle Vault → memory-only folder /run/coroute, never on disk, in git or in logs.
  • Backups: AES-256-GCM encrypted before they leave the gateway.
  • Database: allowlisted servers only, low-privilege schema user.
  • Metrics: only reachable from the server itself (404 through Caddy).
